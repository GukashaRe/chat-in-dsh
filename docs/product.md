# 产品定位与边界

## 一句话定位

在 DeepSeek Harness 左侧面板里，尽量还原 **DeepSeek 官方网页版（限额前）** 的对话体验：官方界面、官方服务端能力、DSH 已登录的 DeepSeek 凭据、独立的本地会话存储。

## 用户应该得到什么

- 界面和交互来自官方 chat-demo，不重画一套“类似”的聊天页
- 智能搜索、深度思考、文件/附件、引用、公式、图表等能力按官方前端行为工作
- 不需要额外填 API Key；使用 DSH 里的 DeepSeek 账户，或已有的 `DEEPSEEK_API_KEY`
- 网页版会话与 DSH 会话分开存储；只有用户主动“导入”时才复制一次
- 长文档遇到扩展模式 32k 限制时自动降级，而不是把错误直接甩给用户
- 官方网页版（限额前）能读的长文档，插件也尽量读完整；不主动接受当前网页版“前 20 页 / 1 万 token”的截断体验

## 非目标

这些不是“以后再说”的待办，除非产品定位被重新讨论：

- **不做通用多模型聊天前端**
  - 不提供模型选择器、模型目录、非 DeepSeek 官方模型路由
  - 不在面板里加 DSH 的模型路由，不新增 `conversation.view`
- **不做网页版与 DSH 会话的双向同步**
  - 导入只是一次性复制；两边各管各的
- **不引入第二套网页登录态**
  - 不为了音色等网页内部能力额外要求用户登录 chat.deepseek.com；是否探索非公开网页接口属于单独产品决策，不默认做
- **不发明网页版没有的 UI**
  - 不新增字号设置、主题设置、模型开关、额外提示条等
  - 浏览器级能力（如页面缩放）可以在不增加常驻 UI 的前提下补齐
- **不承诺服务端能力绝对准确**
  - 同一文件上传两次，服务端解析结果可能有差异；这不是插件能修复的

## 对齐原则

1. **官方前端优先**：能用上游 chat-demo 的行为，就不要另写一套。
2. **官方文案优先**：有官网原文的错误/提示，用原文；没有时才用现有兜底文案。
3. **官方限制优先**：服务端硬限制（20 个文档引用、8MiB 文档文字、1M 上下文）不通过前端猜想来绕开。
4. **DSH 凭据优先**：浏览器不持有密钥；转发层负责鉴权。
5. **沉浸式优先**：能通过快捷键/既有浏览器行为解决的，不加设置项。
